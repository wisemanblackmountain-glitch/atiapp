# Deployment

**ATI ZMATF Executive Training Assessment System**
Render (web service) + Neon (PostgreSQL). Both free tier.

---

## Architecture in one paragraph

Express renders every page server-side. The browser never touches the database
— this process is its only client. That is what keeps the answer key safe: not
a permission that could be misconfigured, but the absence of any route from a
browser to the data. Render's free tier has no persistent disk, so all state
lives in Neon.

---

## 1. Database — Neon

Create a project at [neon.tech](https://neon.tech) (free, no card).

Copy the **pooled** connection string. It looks like:

```
postgresql://user:password@ep-something-pooler.eu-central-1.aws.neon.tech/dbname?sslmode=require
```

Use the pooled endpoint, not the direct one. Render's instance opens and closes
connections as it wakes and sleeps, and the pooler absorbs that.

> **Why not Render's own PostgreSQL?** Free Render databases are **deleted 30
> days after creation**. This system holds official assessment records for a
> government ministry; a 30-day fuse is not acceptable. Neon's free tier has no
> such expiry.

---

## 2. Web service — Render

Dashboard → **New → Blueprint** → select this repository. `render.yaml` defines
everything except the secrets.

Set these in the dashboard (they are marked `sync: false` and are never
committed):

| Variable | Value |
|---|---|
| `DATABASE_URL` | the Neon pooled string from step 1 |
| `ADMIN_USERNAME` | facilitator username |
| `ADMIN_PASSWORD` | 12+ characters, generated not chosen |

`SESSION_SECRET` is generated by Render and left alone.

The start command runs `npm run migrate` before `npm start`. The schema is
idempotent, so a fresh Neon database becomes usable on first boot with no
manual step.

## 3. Seeding — from an operator machine, not the server

Seeding is deliberately **not** part of the deploy.

The 20 questions, 80 options, the answer key and the officer roster are
confidential and gitignored. They are never committed and never copied to the
server. Seeding therefore runs from a machine that holds those source files:

```bash
node database/tools/build-content.js
```

Then, with `DATABASE_URL` pointing at **Neon** rather than local:

```bash
node database/seed.js
```

This writes `participant-credentials.txt` — the only plaintext record of the 32
PINs, because the database stores bcrypt hashes only.

> **Every seed reissues every PIN.** That is the mechanism for a credential
> reissue after an exposure. Use `--keep-pins` for a content-only reseed.
> `--force` is required if attempts already exist, and discards them.

Distribute each officer only their own row, through a private channel. Never
commit that file, attach it to email, or place it in shared cloud storage.

## 4. Keep-alive — the cold-start problem

**Render free instances sleep after 15 minutes of inactivity, and take ~50
seconds to wake.**

On a ten-minute timed assessment that is material: the first officer to sign in
would spend a fifth of their allowance watching a blank tab. The server-side
deadline protects their *score* — the clock starts when they press begin, not
when they open the page — but it is still a bad experience at the worst moment.

Point an external monitor at the health endpoint:

| Setting | Value |
|---|---|
| URL | `https://<service>.onrender.com/healthz` |
| Interval | 10 minutes |
| Expected | HTTP 200, body contains `"status":"ok"` |

[UptimeRobot](https://uptimerobot.com) does this on its free plan. `/healthz` is
mounted **before** the session middleware, so pings never create session rows.

Two caveats worth knowing:

- Continuous uptime consumes roughly 730 of the 750 free instance-hours per
  month. This service fits; a second always-on free service will not.
- Keep the monitor running, but also **load the site yourself two minutes
  before a session starts**. Belt and braces on the one day it matters.

## 5. Verifying a deployment

```bash
curl https://<service>.onrender.com/healthz
```

Expect:

```json
{"status":"ok","store":"postgres","uptime":42}
```

A `503` with `"datastore unreachable"` means the service is up but cannot reach
Neon — check `DATABASE_URL` and whether the Neon project has been suspended for
inactivity.

Then confirm by hand:

1. `/` renders the landing page.
2. `/login` accepts a known participant number, surname and PIN.
3. `/admin/login` accepts the facilitator credentials.
4. A question page shows four options and a running countdown.

## 6. Operational notes

**Single instance only.** The login rate limiter keeps its counters in process
memory. Running two instances would give each its own counters and halve the
effective lockout. Scaling out means moving that state to Postgres first.

**The server owns time.** `public/js/timer.js` is display only. Every mutating
route re-checks `deadline_at`, so a participant with JavaScript disabled, a
paused tab, or an altered system clock changes what they see and nothing else.

**Rotating `SESSION_SECRET`** invalidates every session immediately. That is the
correct response to any suspected exposure, and it is safe to do mid-programme —
officers simply sign in again, and their attempt and deadline are untouched
because both live in the database.

**Backups.** Neon's free tier provides limited history. Before a cohort sits the
assessment, and immediately afterwards, take a manual dump:

```bash
pg_dump "$DATABASE_URL" > ati-backup-$(date +%F).sql
```

Store it somewhere private. This is an official record.
